# SQL schema

The whole schema is in [`sql/migrations/0001_init.sql`](../sql/migrations/0001_init.sql) (no comments there:
a migration is checksummed as a whole file, a comment changes the checksum). This page describes it.

The migration runs with `search_path = <schema>`, so no name in it is schema-qualified.

A job lives in exactly one of four state tables:

```text
scheduled -> enqueued -> claimed -> processed
```

`at` is the time the row entered its state.

Queue, schedule and instance ids are names like `order-42` (`^[a-z0-9][a-z0-9._:-]{0,127}$`), a key is 1-255 characters without control characters. They are checked where they come in (API, `enqueue_v1`), not by a regex CHECK on every write (about 12 us each).

## Entities

### Instances

```sql
CREATE TABLE instances (
    instance_id text PRIMARY KEY,                    -- host:ulid, lower case
    roles       text[] NOT NULL
                CHECK (cardinality(roles) > 0
                       AND roles <@ ARRAY['api', 'ui', 'worker', 'scheduler', 'retention']),
    version     text NOT NULL,
    started_at  timestamptz NOT NULL DEFAULT now(),
    seen_at     timestamptz NOT NULL DEFAULT now(),  -- heartbeat
    stopped_at  timestamptz NULL,                    -- NULL while the instance is live
    flow_cursor text NULL                            -- the cursor of the walk over the undeclared flows
);
```

`flow_cursor` is written by the claim of the instance (`claim_flow_v1`), only when it moves.

### Flows

A flow is the key of a job that limits concurrency and start rate; it promises no order. Only flows with settings
have a row. A name without a row is undeclared and has the defaults: concurrency 1, not paused, no rate limit.
A declaration, a pause, a resume and a removal take the advisory lock of the flow that the claim takes
(`pg_advisory_xact_lock`, until the commit): a change waits for a claim in flight, and a claim sees the limits either
before or after it, never a mix (the jobs by the old rate and the debt by the new one).

```sql
CREATE TABLE flows (
    flow_id     text PRIMARY KEY,               -- 'payments', 'host:api.example.com'
    concurrency int NOT NULL DEFAULT 1
                CHECK (concurrency > 0),        -- jobs running at once
    rate        int NULL
                CHECK (rate > 0),               -- runs per rate_period
    rate_period int NOT NULL DEFAULT 1
                CHECK (rate_period > 0),        -- seconds
    next_at     timestamptz NULL,               -- rate limit (GCRA): when the starts so far are paid off
    paused      boolean NOT NULL DEFAULT false
);
```

### Schedules

`next_id` is the waiting job, which is the template of the next run. `rule`: digits only is an interval in seconds, otherwise cron. `miss_policy`: what to do with the runs missed in downtime: none | one | all.

A removal deletes the waiting run from `scheduled` first and the job only by what that `DELETE` returned: it waits for
a promotion in flight, and a run already moved to `enqueued` stays (a `DELETE FROM jobs` by a subquery would see the
old snapshot and cascade over the promoted job).

```sql
CREATE TABLE schedules (
    schedule_id text PRIMARY KEY,
    rule        text NOT NULL,                -- '300' or '0 9 * * 1-5'
    tz          text NOT NULL DEFAULT 'UTC',  -- of a cron schedule
    next_id     bigint NULL,                  -- the waiting run
    next_at     timestamptz NULL,
    until       timestamptz NULL,
    miss_policy text NOT NULL DEFAULT 'run_once'
                CHECK (miss_policy IN ('skip', 'run_once', 'run_all')),
    paused      boolean NOT NULL DEFAULT false
);
```

### Jobs: what to run (immutable)

```sql
CREATE TABLE jobs (
    id          bigint PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    created_at  timestamptz NOT NULL DEFAULT now(),
    meta        jsonb NOT NULL,  -- sink, target, method, flow_key, priority...
    headers     jsonb NULL,
    body        bytea NULL,
    key         text NULL,       -- idempotency key, unique
    schedule_id text NULL REFERENCES schedules ON DELETE SET NULL,
    -- the job this one answers
    parent_id   bigint NULL REFERENCES jobs ON DELETE SET NULL
);
CREATE UNIQUE INDEX ux_jobs_key  ON jobs (key) WHERE key IS NOT NULL;
CREATE INDEX ix_jobs_schedule_id ON jobs (schedule_id) WHERE schedule_id IS NOT NULL;
CREATE INDEX ix_jobs_parent_id   ON jobs (parent_id, id) WHERE parent_id IS NOT NULL;
```

## States

### 1. scheduled: waits for its time

`scheduled`, `enqueued` and `claimed` live on insert and delete: every claim starts at the head of an index, through the
dead entries. Their autovacuum is set by a small number of dead rows (`autovacuum_vacuum_scale_factor = 0`,
`autovacuum_vacuum_threshold = 1000`, and the same for analyze), not by a share of the table.

```sql
CREATE TABLE scheduled (
    id       bigint PRIMARY KEY REFERENCES jobs ON DELETE CASCADE,
    at       timestamptz NOT NULL,         -- when to run
    attempt  int NOT NULL DEFAULT 0
             CHECK (attempt >= 0),
    flow_key     text NULL,                    -- meta.flow_key
    priority int NOT NULL DEFAULT 0   -- meta.priority, higher runs first
);
CREATE INDEX ix_scheduled_at ON scheduled (at, id);  -- the order of promote: ORDER BY at, id LIMIT n
```

The scheduler moves the due jobs, oldest first, to `enqueued` in one statement (`enqueue_scheduled`). `at` is kept,
so the queue lag counts from the moment the job was due.

A retry with a delay goes back to `scheduled`, whatever its flow.

### 2. enqueued: its time has come, waits for a worker (queue lag = claim time - at)

A job may have both a flow and a priority: the priority orders the rows inside the flow (and the rows without a flow among themselves); it does not rank a flow against others.

`claim_v1` claims a batch in one call (one transaction). By chance (25 % by default) the flows go first, otherwise the
jobs without a flow do; the other part gets the room that is left. Among the flows the declared and the undeclared take
turns the same way (50 %).

- rows without a flow_key: `priority DESC`, `attempt` (new jobs before retries), `id`;
- declared flows: the least loaded first (`running / concurrency`), the places shared in proportion to `concurrency`;
- undeclared flows: one job each, in turn by name from where the previous claim of the instance stopped.

A flow is locked with `pg_try_advisory_xact_lock` (one worker at a time) and gives `concurrency - running` rows
(`priority DESC`, `attempt`, `id`), at most `rate`, nothing before `next_at`. A flow promises no order beyond its
priority.

Every row of `enqueued` is due: a job with a delay waits in `scheduled`. `at` is when the job became due.

```sql
CREATE TABLE enqueued (
    id       bigint PRIMARY KEY REFERENCES jobs ON DELETE CASCADE,
    attempt  int NOT NULL DEFAULT 0
             CHECK (attempt >= 0),
    at       timestamptz NOT NULL DEFAULT now(),  -- since when it waits
    flow_key  text NULL,
    priority int NOT NULL DEFAULT 0
);
CREATE INDEX ix_enqueued_candidates ON enqueued (priority DESC, attempt, id)
    WHERE flow_key IS NULL;
CREATE INDEX ix_enqueued_flow       ON enqueued (flow_key, priority DESC, attempt, id)
    WHERE flow_key IS NOT NULL;
```

### 3. claimed: running

`flow_key` and `priority` are copied from `enqueued`, so a release or a retry puts the job back where it was.

```sql
CREATE TABLE claimed (
    id          bigint PRIMARY KEY REFERENCES jobs ON DELETE CASCADE,
    attempt     int NOT NULL,
    flow_key        text NULL,
    priority    int NOT NULL DEFAULT 0,
    instance_id text NOT NULL,
    at          timestamptz NOT NULL DEFAULT now(),  -- claim time
    until       timestamptz NOT NULL                 -- the lease: released after it
);
CREATE INDEX ix_claimed_flow        ON claimed (flow_key) WHERE flow_key IS NOT NULL;
CREATE INDEX ix_claimed_instance_id ON claimed (instance_id, id);  -- id: lookups by id + instance
```

`id` is in the key of `ix_claimed_instance_id`: the lookups by `id` and `instance_id` (retry, unlock, completion) must
not read all the jobs of the instance (the planner picked this index over the primary key and filtered ~1000 rows a
lookup).

`until` is the lease of the claim. The claim sets it to `now() + p_lease` (30 s), and the heartbeat of the holder renews
it every 5 s for the jobs the worker still holds: from the claim (in its channel or running) to the write of their
outcome, by `(id, attempt)`. The lock reaper of the scheduler releases a job whose lease has ended (`attempt + 1`, so a
late result is rejected); it knows no timeouts. A job is released ≤ 30 s after its holder stopped holding it: the
process died, the write of the outcome failed, or the answer of the claim never came, so the worker never had it.
A long job, or one waiting behind long jobs, is renewed for as long as it is held. `until` has no index: `claimed` is
small and the reaper reads it whole, and the renewal is a HOT update.

### 4. processed: finished

With the response of the target (`outcome` and `headers`; the body only with `--store-response`).

```sql
CREATE TABLE processed (
    id          bigint PRIMARY KEY REFERENCES jobs ON DELETE CASCADE,
    attempt     int NOT NULL,
    instance_id text NOT NULL,
    at          timestamptz NOT NULL DEFAULT now(),
    status      text NOT NULL
                CHECK (status IN ('completed', 'failed', 'cancelled')),
    outcome     jsonb NULL,  -- HTTP status | timeout | error, trace ids; NULL: cancelled
    headers     jsonb NULL,
    body        bytea NULL
);
CREATE INDEX ix_processed_at        ON processed (at);               -- retention
CREATE INDEX ix_processed_status_id ON processed (status, id DESC);  -- UI tabs
```

### History

Journal of state changes, written in the transaction of the change (an outbox); `seq` is the cursor of an indexer.

```sql
CREATE TABLE history (
    seq         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    id          bigint NOT NULL REFERENCES jobs ON DELETE CASCADE,
    attempt     int NOT NULL,
    at          timestamptz NOT NULL DEFAULT now(),
    kind        text NOT NULL
                CHECK (kind IN ('scheduled', 'enqueued', 'claimed', 'released', 'retried',
                                'completed', 'failed', 'cancelled', 'callback')),
    instance_id text NULL,
    message     text NULL
);
CREATE INDEX ix_history_id_seq ON history (id, seq);
```

### Stats

Counters of the UI and the queue metrics, counted by the service on request (`db::stats::queue_stats`): rows per state,
`lag_seconds` (age of the oldest due job), `processed_24h`, `failed_24h`, `instances`. A table of precomputed counters
will come in a migration of its own.
`enqueued` counts every row of `enqueued`; `held` is the part of them that belongs to a flow (they wait for the limits
of their flow: concurrency, rate, pause, or for a worker), so `enqueued - held` wait for a worker. `lag_seconds`
ignores the held jobs: a flow keeps its jobs back by design, so only a job without a flow that waits is a lack of
workers. A job of a flow that has a free place and waits for a worker is counted as held too (a flow's jobs are not
told apart by whether the flow is blocked). The same numbers go to `irisqo.queue.depth{state=enqueued}`,
`irisqo.queue.held` and `irisqo.queue.lag`. How long the jobs of the flows wait is `irisqo.job.queue.duration`, recorded
at each claim by the class of the flow.

## Functions

### enqueue_v1

`enqueue_v1(job jsonb) RETURNS bigint`: enqueues inside the caller's transaction (embedded mode) and returns the
job id. `job` is a JSON object, the same fields as `POST /api/v1/jobs` but the schedule (`cron`, `interval`, `tz`, `until`).
A field that is not known is refused, of the job, its callback or a retry policy: a typo is an error,
not a default.

```text
url (http, https; noop://… is the noop sink)
method (default POST), headers (object of strings), body (a string as it is, any other JSON as JSON text with content-type application/json) | body_base64
at (RFC 3339 or unix seconds, 1970 to 9999) | delay (seconds), timeout (ms; none: --timeout when the job runs)
retry (none: no retries) { policy fixed | fibonacci | exponential, count (up to 9999),
      delay (seconds; fixed without it retries at once), max_delay (seconds, backoffs) },
      delays up to 604800; an object only (the text of _retry is for the API)
callback (object; see docs/callbacks.md) { url, method, mode, types, headers, retry (as above),
      timeout, flow_key, priority }
flow_key, priority, key (a repeated key returns the existing job id)
traceparent, tracestate
```

Only the format is checked, not the target (no DNS, no private-address check). Notes on the function body:

- the sink comes from `url`: `noop://…` is the `noop` sink, any other URL an `http` one;
- `c_url`, an http(s) URL of the characters of RFC 3986 only
  (`[user@]host[:port][path][?query][#fragment]`), is narrower than what the server reads: a URL
  that passes is one the server can read;
- the fields that are not known are named in the error (`fields that are not known: a, b`), of
  the job and of its callback;
- a retry policy is an object; no retries said out loud is `{"policy": "fixed", "count": 0}`,
  where an absent (or null) policy means a default (a callback);
- the policy is stored as it is, so it has no other field and its numbers are JSON numbers; the
  nulls in it are stripped with the rest of the meta;
- `at` is a usable time, as the API takes it: from 1970 up to 9999-12-31; an RFC 3339 time that
  is not a date (`02-30`) fails the cast and is refused as one out of range;
- a time in the past runs the job now; `delay` is NULL when there is no delay;
- the job meta has the same shape as the one written by the service;
- when the key already exists the call is an idempotent repeat and returns the existing job id.

### claim_v1

`claim_v1(p_instance_id text, p_limit int, p_lease interval, p_flow_share int DEFAULT 25, p_declared_share int DEFAULT
50) RETURNS TABLE (id, meta, headers, body, schedule_id, key, attempt, waited, flow_declared)`: claims up to `p_limit`
jobs for a worker, `enqueued` -> `claimed`, and returns them with the columns of `jobs` that a worker needs (one call,
one transaction). Each claim has the lease `now() + p_lease` (`claimed.until`). `waited` is the seconds from
`enqueued.at` to the claim; `flow_declared` is `true` for a declared flow, `false` for an undeclared one and `NULL`
without a flow. The service records them as `irisqo.job.queue.duration` (`job.flow`: `declared`, `undeclared`, `none`).

```sql
SELECT * FROM claim_v1($1, $2, interval '30 seconds')
```

With the chance `p_flow_share` percent it calls `claim_flow_v1` first and `claim_plain_v1` with the rest, otherwise the
other way round (`GET DIAGNOSTICS ROW_COUNT` counts the first part). A fixed order starved the second part: while the
jobs without a flow filled every batch, no flow started at all; a chance per claim (as Sidekiq orders its queues) gives
the flows about one claim in four, and the first part of a claim may take the whole batch. The flows go first only
when `enqueued` has a job of a flow (one probe of `ix_enqueued_flow`): without one, the walk over the flows found
nothing and cost a claim of jobs without a flow about 0.3 ms. The probe is `ORDER BY flow_key LIMIT 1`, not `EXISTS`:
before the first `ANALYZE` of `enqueued` the planner took `EXISTS` for a seq scan, which reads every row when no
job has a flow (8 ms for 200 000). `jit` is off: the planner overestimates the flow part and JIT compilation took about
250 ms per call.

Each part is one statement after its checks: it deletes the rows from `enqueued`, writes `history`, inserts into
`claimed` and returns the jobs (`priority DESC`, `attempt`, `id`); the flow part also moves `next_at` of a rate-limited
flow. The jobs without a flow keep their own one-statement function: they are the fast path of most claims.

### claim_plain_v1

`claim_plain_v1(p_instance_id text, p_limit int, p_lease interval) RETURNS TABLE (id, meta, headers, body, schedule_id, key, attempt, waited)`:
the jobs without a flow. Claims up to `p_limit` jobs (`priority DESC`, `attempt`, `id`; `FOR UPDATE SKIP LOCKED`, the
partial index `ix_enqueued_candidates`) in one statement: `enqueued` -> `claimed`, `history`, and the jobs are returned.

### claim_flow_v1

`claim_flow_v1(p_instance_id text, p_limit int, p_lease interval, p_declared_share int)` returns the
columns of `claim_v1`: the jobs of the flows. A flow runs at most `concurrency` jobs at once (1 when it is not declared), starts
nothing while it is paused, and limits the start rate by GCRA (below). No order is promised: a flow gives its jobs by
`priority DESC`, `attempt`, `id`, but a retry or a released job goes back with its place lost.

The declared and the undeclared flows are picked by their own functions, which only lock flows and choose the ids:
with the chance `p_declared_share` percent `claim_declared_ids_v1` goes first and `claim_undeclared_ids_v1` gets the
rest, otherwise the other way round. Ahead of the undeclared ones without that, a declared flow with a high
`concurrency` and a backlog would take every batch. Then one statement claims all the chosen ids. The class of a name is
found at the claim, not stored: declaring or removing a name with waiting jobs changes nothing else.

The rate is a leaky bucket kept in one timestamp, `next_at`: the time by which the starts so far are paid off. Every
start adds `T = rate_period / rate` to it (`next_at = greatest(next_at, now()) + n * T`). The debt is
`D = max(next_at - now(), 0)` and the bucket holds one period, so `remaining = floor((rate_period - D) * rate /
rate_period)` starts are free right now: `rate` after an idle period, then one more every `T`. A flow is ready when
`remaining >= 1` and takes at most `remaining` jobs. `NULL` `next_at` is an empty debt. A new declaration keeps the
spent share of the bucket: `next_at = now() + D * new_period / old_period` (`NULL` without a rate), so a repeated `PUT`
changes nothing, a new rate refills at its own pace and a shorter period shortens the debt in proportion. `flow_rate_free_v1(rate,
rate_period, next_at)` computes `remaining`: the starts a flow can make right now, `2147483647` without a rate (so an
undeclared flow is not limited). The flow list reads the same function (`rate_left`, `null` without a rate), so the UI
and the claim agree. It has no `SET search_path` on purpose: a SQL function with a `SET` clause is not inlined into the
query that calls it, and it uses only built-ins. Within any window of one period
at most about `2 * rate` jobs can start (a full bucket, then its refill); the long-run rate is `rate / rate_period`.

Both functions work in two steps. Step 1 locks the flows that can start a job. The locks are taken in a statement of
their own: the next statement reads `claimed` after them, so two workers never fill the same free place. Step 2 reads
`claimed`, `concurrency` and the rate again with its own snapshot, taken after the locks, and chooses the ids; `paused` is
not checked again on purpose: a pause that commits between the two steps may let this claim start jobs, the next claim
sees it.

`claim_declared_ids_v1(p_limit int) RETURNS bigint[]` walks the rows of `flows` (there are few). Step 1 keeps the flows
that are not paused, have a free start (`remaining >= 1`), have waiting jobs and are not full, and tries their locks
from the least loaded (`running / concurrency`, ties by chance, so that no name wins every tie). Step 2 takes up to
`least(concurrency - running, remaining)` jobs of each locked flow (`priority DESC`, `attempt`, `id`) and fills the
batch "by water level": every candidate job is ranked by the load its flow would have with it, `(running + k) /
concurrency` for the `k`-th job of the flow, and the `p_limit` lowest ranks win. So the places are shared in proportion
to `concurrency` within one claim: with 100 and 10 free and 64 places, 59 and 5. The weight is `concurrency` for now.

`claim_undeclared_ids_v1(p_limit int, p_flow_cursor text, OUT o_ids bigint[], OUT o_after text)` walks the distinct waiting
names (index skip scan on `ix_enqueued_flow`, one probe per name) in turn: first after `p_flow_cursor`, then from the start up
to `p_flow_cursor`. It looks at `p_limit * 4` names at most (`seen`): a name whose job runs is passed over, and thousands of
busy names made a claim walk them all (65 ms for 10 000 instead of 2 ms). `ready` keeps the names without a row in
`flows` and without a job in `claimed`; the walk is lazy and stops after `p_limit` locked names. Step 2 takes one job of
each locked name, again only when it has no row in `flows` and no job in `claimed`: a declaration that commits between
the steps moves the name to the declared part. `o_after` is where the walk stopped: the last locked name when the places
ran out, otherwise the last name looked at (`p_flow_cursor` when there was none). So an empty claim moves on too, and a free
name behind many busy ones is reached within a few claims. `claim_flow_v1` reads `p_flow_cursor` from `instances.flow_cursor`
of the instance and writes `o_after` back when it moved: each instance keeps its own, so a name waits about (ready names
/ batch) claims, not behind the names before it in the alphabet. An instance without a row walks from the start every
time. In
`ready` the `NOT EXISTS` checks carry `OFFSET 0`: without it the planner turns them into an anti join that hashes the
whole walk, reads every name and loses the order. The function runs with `enable_seqscan` off: the planner scanned the
small `flows` once per name (150 ms for 10 000 names instead of 50 ms).

### Why the jobs are returned by the claim

The claim functions read the jobs in the statement that claims them. Every statement of a plpgsql function takes a fresh
snapshot, so a join with `jobs` outside the function (`... FROM claim_v1(..) c JOIN jobs j`) would use an older one and
drop a job enqueued meanwhile: it would stay in `claimed` and never run until the lock reaper released it.
