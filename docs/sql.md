# SQL schema

The whole schema is in [`sql/migrations/0001_init.sql`](../sql/migrations/0001_init.sql) (no comments there:
a migration is checksummed as a whole file, a comment changes the checksum). This page describes it.

The migration runs with `search_path = <schema>`, so no name in it is schema-qualified.

A job lives in exactly one of four state tables:

```text
scheduled -> enqueued -> claimed -> processed
```

`at` is the time the row entered its state.

Queue, schedule and instance ids are names like `order-42` (`^[a-z0-9][a-z0-9._:-]{0,127}$`), a key is 1-255 characters without control characters. They are checked where they come in (API, `enqueue_v1`), not by a regex CHECK on every write (about 12 us each).

## Entities

### Instances

```sql
CREATE TABLE instances (
    instance_id text PRIMARY KEY,                    -- host:ulid, lower case
    roles       text[] NOT NULL
                CHECK (cardinality(roles) > 0
                       AND roles <@ ARRAY['http', 'worker', 'scheduler', 'retention', 'relay']),
    version     text NOT NULL,
    started_at  timestamptz NOT NULL DEFAULT now(),
    seen_at     timestamptz NOT NULL DEFAULT now(),  -- heartbeat
    stopped_at  timestamptz NULL                     -- NULL while the instance is live
);
```

### Flows

A flow is the key of a job that limits concurrency and start rate; it promises no order. Only flows with settings
have a row. A name without a row is undeclared and has the defaults: concurrency 1, not paused, no rate limit.

```sql
CREATE TABLE flows (
    flow_id     text PRIMARY KEY,               -- 'payments', 'host:api.example.com'
    concurrency int NOT NULL DEFAULT 1
                CHECK (concurrency > 0),        -- jobs running at once
    rate        int NULL
                CHECK (rate > 0),               -- runs per rate_period
    rate_period int NOT NULL DEFAULT 1
                CHECK (rate_period > 0),        -- seconds
    next_at     timestamptz NULL,               -- rate limit (GCRA): when the starts so far are paid off
    paused      boolean NOT NULL DEFAULT false
);
```

### Schedules

`next_id` is the waiting job, which is the template of the next run. `rule`: digits only is an interval in seconds, otherwise cron. `miss_policy`: what to do with the runs missed in downtime: none | one | all.

```sql
CREATE TABLE schedules (
    schedule_id text PRIMARY KEY,
    rule        text NOT NULL,                -- '300' or '0 9 * * 1-5'
    tz          text NOT NULL DEFAULT 'UTC',  -- of a cron schedule
    next_id     bigint NULL,                  -- the waiting run
    next_at     timestamptz NULL,
    until       timestamptz NULL,
    miss_policy text NOT NULL DEFAULT 'run_once'
                CHECK (miss_policy IN ('skip', 'run_once', 'run_all')),
    paused      boolean NOT NULL DEFAULT false
);
```

### Jobs: what to run (immutable)

```sql
CREATE TABLE jobs (
    id          bigint PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    created_at  timestamptz NOT NULL DEFAULT now(),
    meta        jsonb NOT NULL,  -- sink, target, method, flow_key, priority...
    headers     jsonb NULL,
    body        bytea NULL,
    key         text NULL,       -- idempotency key, unique
    schedule_id text NULL REFERENCES schedules ON DELETE SET NULL,
    -- the job this one answers
    parent_id   bigint NULL REFERENCES jobs ON DELETE SET NULL
);
CREATE UNIQUE INDEX ux_jobs_key  ON jobs (key) WHERE key IS NOT NULL;
CREATE INDEX ix_jobs_schedule_id ON jobs (schedule_id) WHERE schedule_id IS NOT NULL;
CREATE INDEX ix_jobs_parent_id   ON jobs (parent_id) WHERE parent_id IS NOT NULL;
```

## States

### 1. scheduled: waits for its time

`scheduled`, `enqueued` and `claimed` live on insert and delete: every claim starts at the head of an index, through the
dead entries. Their autovacuum is set by a small number of dead rows (`autovacuum_vacuum_scale_factor = 0`,
`autovacuum_vacuum_threshold = 1000`, and the same for analyze), not by a share of the table.

```sql
CREATE TABLE scheduled (
    id       bigint PRIMARY KEY REFERENCES jobs ON DELETE CASCADE,
    at       timestamptz NOT NULL,         -- when to run
    attempt  int NOT NULL DEFAULT 0
             CHECK (attempt >= 0),
    flow_key     text NULL,                    -- meta.flow_key
    priority int NOT NULL DEFAULT 0   -- meta.priority, higher runs first
);
CREATE INDEX ix_scheduled_at ON scheduled (at);
```

A retry with a delay goes back to `scheduled`, whatever its flow.

### 2. enqueued: its time has come, waits for a worker (queue lag = claim time - at)

A job may have both a flow and a priority: the priority orders the rows inside the flow (and the rows without a flow among themselves); it does not rank a flow against others.

`claim_v1` claims a batch in one call (one transaction): first the jobs without a flow (`claim_plain_v1`), then the
flows get the room that is left (`claim_flow_v1`).

- rows without a flow_key: `priority DESC`, `attempt` (new jobs before retries), `id`;
- flows, only when the first part did not fill the batch. A flow is locked with `pg_try_advisory_xact_lock`
  (one worker at a time) and gives `concurrency - running` rows (`priority DESC`, `attempt`, `id`), at most `rate`, nothing
  before `next_at`. A flow promises no order beyond its priority.

Every row of `enqueued` is due: a job with a delay waits in `scheduled`. `at` is when the job became due.

```sql
CREATE TABLE enqueued (
    id       bigint PRIMARY KEY REFERENCES jobs ON DELETE CASCADE,
    attempt  int NOT NULL DEFAULT 0
             CHECK (attempt >= 0),
    at       timestamptz NOT NULL DEFAULT now(),  -- since when it waits
    flow_key  text NULL,
    priority int NOT NULL DEFAULT 0
);
CREATE INDEX ix_enqueued_candidates ON enqueued (priority DESC, attempt, id)
    WHERE flow_key IS NULL;
CREATE INDEX ix_enqueued_flow       ON enqueued (flow_key, priority DESC, attempt, id)
    WHERE flow_key IS NOT NULL;
```

### 3. claimed: running

`flow_key` and `priority` are copied from `enqueued`, so a release or a retry puts the job back where it was.

```sql
CREATE TABLE claimed (
    id          bigint PRIMARY KEY REFERENCES jobs ON DELETE CASCADE,
    attempt     int NOT NULL,
    flow_key        text NULL,
    priority    int NOT NULL DEFAULT 0,
    instance_id text NOT NULL,
    at          timestamptz NOT NULL DEFAULT now()  -- claim time
);
CREATE INDEX ix_claimed_flow        ON claimed (flow_key) WHERE flow_key IS NOT NULL;
CREATE INDEX ix_claimed_instance_id ON claimed (instance_id);
CREATE INDEX ix_claimed_at          ON claimed (at);  -- the lock reaper
```

### 4. processed: finished

With the response of the target (`outcome` and `headers`; the body only with `--store-response`).

```sql
CREATE TABLE processed (
    id          bigint PRIMARY KEY REFERENCES jobs ON DELETE CASCADE,
    attempt     int NOT NULL,
    instance_id text NOT NULL,
    at          timestamptz NOT NULL DEFAULT now(),
    status      text NOT NULL
                CHECK (status IN ('completed', 'failed', 'cancelled')),
    outcome     jsonb NULL,  -- HTTP status | timeout | error, trace ids; NULL: cancelled
    headers     jsonb NULL,
    body        bytea NULL
);
CREATE INDEX ix_processed_at        ON processed (at);               -- retention
CREATE INDEX ix_processed_status_id ON processed (status, id DESC);  -- UI tabs
```

### History

Journal of state changes, written in the transaction of the change (an outbox); `seq` is the cursor of an indexer.

```sql
CREATE TABLE history (
    seq         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    id          bigint NOT NULL REFERENCES jobs ON DELETE CASCADE,
    attempt     int NOT NULL,
    at          timestamptz NOT NULL DEFAULT now(),
    kind        text NOT NULL
                CHECK (kind IN ('scheduled', 'enqueued', 'claimed', 'released', 'retried',
                                'completed', 'failed', 'cancelled', 'callback')),
    instance_id text NULL,
    message     text NULL
);
CREATE INDEX ix_history_id_seq ON history (id, seq);
```

### Stats

Counters of the UI, counted by `refresh_stats_v1` instead of on every page request: rows per state, `lag_seconds` (age of the oldest due job), `processed_24h`, `failed_24h`, `instances`.
`enqueued` counts every row of `enqueued`; `held` is the part of them that belongs to a flow (they wait for the limits
of their flow: concurrency, rate, pause, or for a worker), so `enqueued - held` wait for a worker. `lag_seconds`
ignores the held jobs: a flow keeps its jobs back by design, so only a job without a flow that waits is a lack of
workers. A job of a flow that has a free place and waits for a worker is counted as held too (a flow's jobs are not
told apart by whether the flow is blocked). The same numbers go to `irisqo.queue.depth{state=enqueued}`,
`irisqo.queue.held` and `irisqo.queue.lag`.

```sql
CREATE TABLE stats (
    name  text PRIMARY KEY,
    value bigint NOT NULL,
    at    timestamptz NOT NULL  -- when it was counted
) WITH (fillfactor = 50);         -- few rows rewritten all the time: room for HOT updates
```

## Functions

### enqueue_v1

`enqueue_v1(job jsonb) RETURNS bigint`: enqueues inside the caller's transaction (embedded mode) and returns the
job id. `job` is a flat JSON object, the same fields as `POST /api/v1/jobs` and `PUT /api/v1/schedules/{id}`;
`sink` is required (`http` also needs `url`):

```text
sink http | noop
url, method (default POST; sink http), headers (object of strings), body (a string as it is, any other JSON as JSON text with content-type application/json) | body_base64
at (unix time) and/or delay (seconds; at wins), timeout (ms; none: --timeout when the job runs)
retry none (default) | fixed | fibonacci | exponential, retry_count,
      retry_delay (seconds; fixed without it retries at once), retry_max_delay (seconds, backoffs)
flow_key, priority, key (a repeated key returns the existing job id)
traceparent, tracestate
```

Only the format is checked, not the target (no DNS, no private-address check). Notes on the function body:

- a time in the past runs the job now; `delay` is NULL when there is no delay;
- the job meta has the same shape as the one written by the service;
- when the key already exists the call is an idempotent repeat and returns the existing job id.

### promote_v1

`promote_v1(p_instance_id text, p_limit int) RETURNS int`: moves up to `p_limit` due jobs, oldest first:
`scheduled` -> `enqueued`. `at` is kept, so the queue lag counts from the moment the job was due. Returns the number
of jobs moved.

### refresh_stats_v1

`refresh_stats_v1(p_max_age interval DEFAULT '2 seconds') RETURNS boolean`: recounts `stats` unless it is younger
than `p_max_age`. One advisory lock lets one caller count while the others read the old numbers. Returns true when
this call counted. After taking the lock the age is checked again: the previous holder may have counted just now.

### claim_v1

`claim_v1(p_instance_id text, p_limit int) RETURNS TABLE (id, meta, headers, body, schedule_id, key, attempt)`: claims
up to `p_limit` jobs for a worker, `enqueued` -> `claimed`, and returns them with the columns of `jobs` that a worker
needs: the jobs without a flow first, then the flows with what is left (one call, one transaction).

```sql
SELECT * FROM claim_v1($1, $2)
```

It calls `claim_plain_v1` and, when that gave less than `p_limit` rows, `claim_flow_v1` with the rest (`GET DIAGNOSTICS
ROW_COUNT` counts the first part). `jit` is off: the planner overestimates the flow part and JIT compilation took about
250 ms per call.

Each of the two is one statement after its checks: it deletes the rows from `enqueued`, writes `history`, inserts into `claimed` and returns the jobs
(`priority DESC`, `attempt`, `id`); `claim_flow_v1` also moves `next_at` of a rate-limited flow.

### claim_plain_v1

`claim_plain_v1(p_instance_id text, p_limit int) RETURNS TABLE (id, meta, headers, body, schedule_id, key, attempt)`:
the jobs without a flow. Claims up to `p_limit` jobs (`priority DESC`, `attempt`, `id`; `FOR UPDATE SKIP LOCKED`, the
partial index `ix_enqueued_candidates`) in one statement: `enqueued` -> `claimed`, `history`, and the jobs are returned.

### claim_flow_v1

`claim_flow_v1(p_instance_id text, p_limit int)` returns the same columns: the jobs of the flows. A flow runs at most
`concurrency` jobs at once (1 when it is not declared), starts nothing while it is paused, and limits the start rate by
GCRA (below). No order is promised: a flow gives its jobs by `id`, but a retry or a released job goes back with its
place lost.

The rate is a leaky bucket kept in one timestamp, `next_at`: the time by which the starts so far are paid off. Every
start adds `T = rate_period / rate` to it (`next_at = greatest(next_at, now()) + n * T`). The debt is
`D = max(next_at - now(), 0)` and the bucket holds one period, so `remaining = floor((rate_period - D) * rate /
rate_period)` starts are free right now: `rate` after an idle period, then one more every `T`. A flow is ready when
`remaining >= 1` and takes at most `remaining` jobs. `NULL` `next_at` is an empty debt. `flow_rate_free_v1(rate,
rate_period, next_at)` computes `remaining`: the starts a flow can make right now, `2147483647` without a rate (so an
undeclared flow is not limited). The flow list reads the same function (`rate_left`, `null` without a rate), so the UI
and the claim agree. It has no `SET search_path` on purpose: a SQL function with a `SET` clause is not inlined into the
query that calls it, and it uses only built-ins. Within any window of one period
at most about `2 * rate` jobs can start (a full bucket, then its refill); the long-run rate is `rate / rate_period`.

Step 1 locks the flows that can start a job (`v_flows`). The locks are taken in a statement of their own: the next
statement reads `claimed` after them, so two workers never fill the same free place. Inside it, the recursive `names`
finds the distinct waiting flows (index skip scan on `ix_enqueued_flow`, one probe per name), `ready` keeps the ones
that are not paused, have a free start (`remaining >= 1`) and are not full (`MATERIALIZED`, so the lock is taken after these checks).

Step 2 takes the free places of the locked flows (`concurrency - running`, at most `remaining`) and the ids of that many
jobs per flow (`priority DESC`, `attempt`, `id`), at most `p_limit` in all, deletes them from `enqueued`, writes `history`, inserts into `claimed`, moves `next_at` of a rate-limited flow and returns the jobs.

### Why the jobs are returned by the claim

The claim functions read the jobs in the statement that claims them. Every statement of a plpgsql function takes a fresh
snapshot, so a join with `jobs` outside the function (`... FROM claim_v1(..) c JOIN jobs j`) would use an older one and
drop a job enqueued meanwhile: it would stay in `claimed` and never run until the lock reaper released it.
